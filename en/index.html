Tenjin Onboarding Guide

New to Tenjin? This page walks you through what to set up, how Tenjin's data rules work, and how to check things when numbers don't match after launch.

This page is a map. The detailed steps live in the official docs. The 📖 Official docs box at the top of each section links to the full instructions for that step. This page tells you what needs to be done, in what order, and where people most often go wrong.
Open Tenjin docs ↗

The core work is four steps: add your app (1) → integrate the SDK (2) → connect channels (3) → set up callbacks (5). Everything else is as needed.

New to the dashboard? Start with Dashboard map: where things are. The steps below will make a lot more sense.

Numbers don't match after launch? Go straight to Troubleshooting · Data discrepancy checklist. The first four checks rule out most cases.

Common Q&A

Third-party Android stores need their own app

Google Play and other Android stores (Xiaomi / OPPO / vivo / Transsion) are separate apps in Tenjin. Builds for Chinese stores are added as Android Other apps in the dashboard; in the SDK, use TenjinSDK.AppStoreType.other together with that app's SDK Key.

Which one to use depends on which build is installed on the user's phone, not on which channel you advertise on. For example, if you advertise on OPPO but users download from Google Play after clicking, use the Google Play app.

Key rule: the store type declared in the SDK must exactly match the type selected in the dashboard. A mismatch returns {"code":404,"message":"no such app"}.

You can add an app before it's published

Go to CONFIGURE → Apps → + Add New App, click Add Manually, pick the platform (Apple / Google Play / Amazon / Android Other), and enter the app name and bundle ID. Once the app is live, Tenjin fills in the store details automatically (up to about 24 hours), or you can click Update App Store Info on the app page.

Add the app and the channel before creating a campaign

Otherwise the app dropdown is empty when you create a campaign (it shows No options).

Common Q&A

A log line doesn't mean the SDK is actually connected

The most common false signal: the client log shows "connect", but the dashboard shows the SDK Key as Last used: never and App Open not received. That means no request ever reached Tenjin.

Also keep initialization and connect apart: initialization (initialize on iOS, getInstance(key) on Unity / Android) only creates the instance and sends nothing. The request to Tenjin is sent by connect(). On iOS the order is: initialize → ATT prompt → connect().

Why does getAttributionInfo return empty or missing fields?

Attribution isn't instant. After connect(), the server has to receive the request, match it to a click and produce a result. A few seconds is the industry-standard delay, so if you query too early the result may still be processing. Add retry logic on the client:

  • Don't delay connect(). Call it right after privacy consent (Android) or the ATT choice (iOS)
  • Make the first getAttributionInfo call 2–3 seconds after connect()
  • If the response is empty or missing key fields, wait 1–2 seconds and retry
  • Cap retries at 3–5 attempts
iOS: show the ATT prompt before starting the SDK

The SDK records the ATT status on first launch. If the user hasn't answered the prompt yet, it records "not authorized", which badly understates your ATT opt-in rate. Start the Tenjin SDK after the user has responded to the ATT prompt.

Using Cocos or another engine / framework?

Besides iOS, Android and Unity, Tenjin officially supports Flutter, React Native and more. Cocos and some other engines have unofficial community plugins, listed in the Other Plugins doc.

Other plugins
Don't integrate the Tenjin SDK and the Meta SDK together

Both SDKs would report the same events and Meta's numbers get messy. If Tenjin is your MMP, don't add the Meta SDK; at a minimum, turn off autoLogAppEventsEnabled in Meta's settings so it stops sending revenue / purchase events by default.

3Connecting channels▶
What to doAdd and authorize channels in the dashboard → complete each channel's own setup → create campaigns and tracking links (for non-self-attributing channels)
Add channels Create campaigns and tracking links
Done when: spend data is pulled from the channel, and Tracked Installs appear once campaigns are live

What this step is really for:

  • You add a channel and create a campaign in order to generate a tracking link, which you then paste into the channel's ad platform.
  • How many links you need depends on the channel. For most channels, one tracking link per app is enough; later campaigns don't need to be added one by one in Tenjin because they're pulled from the channel. But some channels (OPPO, for example) need a separate tracking link for each campaign: every time you create a campaign on the channel, create a matching link in Tenjin, or that campaign's data won't be attributed correctly.
  • Some self-attributing networks (SANs) have no tracking link at all. That's expected.

Every channel names its "campaign" levels differently; see the channel hierarchy mapping.

The four sections below cover Meta, Google Ads, TikTok and other channels.

Common Q&A

A channel Campaign ID showing "unknown" is normal

This field is only resolved once the campaign actually produces attributed data, so it shows unknown when first created. But if it still shows unknown after launch and clicks are also 0, check the macro mapping in the tracking link.

3.1Channel: MetaFrequent▶
Meta setup Meta AMM and Tenjin
⚠️ Most common issue: accept the AMM terms before you launch

Under Meta's privacy rules, Tenjin can show full Meta data only if either condition is met:

① the campaign meets the minimum volume threshold (>100 unique users or >100 tracked installs), or ② you have accepted Meta's AMM (Advanced Mobile Measurement) terms.

Open Meta's AMM terms to accept Docs: Meta privacy threshold

If neither is met, Meta only allows part of the data to be shown: Meta's dashboard shows dozens or hundreds of installs, while Tenjin's campaign / creative / daily breakdowns only show some of them. App-level and channel-level totals are not affected. Accept the AMM terms before you start spending, rather than waiting for volume.

Accepting is not retroactive: the day you accept has partial data, and data is complete from the next day. For dates before acceptance, you can only see App / channel level totals. Those totals are complete and nothing is lost; Meta just doesn't allow more detailed breakdowns. So a total that's larger than the sum of its breakdown is expected, not a data error. To get more detail for a past period, widen the date range or use fewer breakdown levels.

Why Meta data looks incomplete before AMM was accepted
Android: we recommend adding the Install Referrer decryption key

Meta passes ad information to the app's first open through the Android Install Referrer. With the decryption key added, Tenjin gets an additional, more accurate way to attribute Android installs.

  • Where to get it: Meta for Developers → your app → App Settings → Basic → Android section; copy the Install Referrer Decryption Key.
  • Where to enter it: Tenjin app page → Settings tab → Advanced → Meta Referrer Decryption Key.
  • The SDK needs Install Referrer integrated (see the Android SDK doc).
Android Meta Install Referrer setup
What do I set up in Tenjin to run AEO / VO campaigns?
  • AEO (app event optimization): on the app page, go to Callbacks → Meta → ADD EVENTS, choose Meta standard custom event, and map your event to a Meta standard event. To optimize on your own event names, choose Meta manual custom event, but you need at least one non-install standard event first.
  • VO (value optimization): run AEO first. To optimize on purchase value, turn on the Meta IAP callback; for ad revenue value, turn on the Meta Ad Revenue callback. Meta's eligibility bar: at least 15 attributed purchases with value in the last 7 days, or at least 15 attributed ad impressions with at least 2 distinct values in the last 28 days.

Once set up, you can see the events Tenjin sends in Meta Events Manager.

3.2Channel: Google AdsFrequent▶
Google Ads setup
⚠️ iOS requires ICM

For iOS users who haven't opted in to ATT, Google attributes probabilistically through ICM (Integrated Conversion Measurement). It's currently Google's only probabilistic attribution method on iOS. Without ICM, these users basically can't be attributed to Google, and Tracked Installs will be noticeably low.

Once ICM is integrated in the SDK per the docs, Tenjin claims these installs automatically. Also set the Google Ads probabilistic attribution window to 24 hours (app page → Attribution tab → choose Google Ads and set it separately).

Google Ads ICM (step 1)
Primary or Secondary conversion action? It depends on which source you bid on

Google Ads only bids on "Primary" conversions. Tenjin's conversion event is Secondary by default after import. Whether to change it depends on which source you want Google to optimize toward:

Your situationHow to set it
Bidding on Tenjin's conversionsSet the Tenjin conversion to Primary and Firebase to Secondary
Bidding on Firebase, e.g. running tROAS on ad revenue (Google only accepts ad revenue sent from Firebase)Set Firebase to Primary and keep Tenjin as Secondary

From the docs: setting Firebase as the primary conversion can increase the gap between Tracked Installs and Reported Installs. This comes from the two sides attributing differently. It's expected and doesn't mean anything is wrong on Tenjin's side.

How to change it: Google Ads → open the conversion (named like your.package first_open) → Edit Settings → change Action optimization. After a change, Smart Bidding needs 1–2 conversion cycles to relearn, so the effect shows up gradually.

Import conversion events from Tenjin (step 4)
Multiple Google Ads accounts: add one callback per Link ID

From the docs: "If you have multiple Link IDs, click + ADD EVENTS → Advanced and add a callback for each Link ID respectively."

Add your Link ID in Tenjin (step 3)
Can't select Tenjin as a conversion source in Google Ads? It needs real installs first

Even with the link created and callbacks added, Google Ads only lists third-party app analytics as a source after it has actually received install callbacks under that Link ID. Right after linking, with zero installs, it won't appear.

This isn't a setup error. Release the production build, wait for real installs, then come back after a few hours to a day.

Can't change the conversion action?

Check whether it's a Manager Account (MCC) permission restriction, and confirm the campaign goal is set to "Installs".

Where do I create a Link ID in Google Ads?

In Google Ads, go to Tools → Data Manager → Connected products → Third-party app analytics, click + Link ID, and choose Tenjin and your app. "Unverified" is normal at first; it changes once you've added it in Tenjin and conversion data starts flowing.

Can ad revenue be sent to Google Ads for tROAS?

Not through Tenjin (or any MMP) for now. Ad revenue for Google Ads tROAS must be sent directly from Firebase. Tenjin still handles attribution and the ROAS in its own dashboard; the two run side by side.

3.3Channel: TikTok▶
TikTok for Business setup TikTok discrepancy troubleshooting guide
TikTok uses an App Integration Key, not a tracking link
  1. Add your TikTok account in Tenjin, then create a TikTok campaign and get the App Integration Key under Tracking.
  2. In TikTok Events Manager, connect a data source, choose Tenjin as the MMP and paste the key. TikTok can take up to 24 hours to set up tracking.
  3. Enter the TikTok App ID that TikTok gives you back in Tenjin: app page → Callbacks → choose TikTok, then turn on the Install callback.
Stuck on "Pending Verification" in TikTok?

First confirm all three steps above are done and the TikTok App ID is correct. If everything is right, TikTok's own verification can take a few days.

Can't find a new ad account in Tenjin?

In TikTok Business Center, add the TikTok account you originally authorized in Tenjin as a member of the new ad account and grant it permission. Then click Add Ad Account in Tenjin and search; re-authorizing is usually not needed.

TikTok campaigns appear in Tenjin as "ad group name (campaign name)"

The name in brackets is the TikTok campaign the ad group belongs to. Requests at campaign level to the TikTok API don't return platform and bundle_id, so Tenjin has to request at ad group level. This is a reporting architecture limit and can't be changed.

Supported mediation platforms and code Ad revenue channel API setup The two types of ad revenue

Common Q&A

Mediation platforms are integrated in the SDK, not added as channels

Ad monetization is a separate SDK integration: the Tenjin SDK listens for the mediation platform's impression events. A mediation platform isn't an ad channel and doesn't need to be added as one. Supported platforms and their integration code are in the docs.

Your mediation platform isn't on the supported list?

The SDK has a generic custom method (Android SDK 1.19.0+): pass each impression's revenue to Tenjin as JSON, with network name, currency and revenue required. See the Custom mediation section of each platform's SDK doc.

How do I tell UA channels from monetization channels?

On the Add a Channel page, cards marked revenue in the bottom-right corner are monetization channels; cards marked attribution and spend are UA channels.

Why does ad revenue show up in the UA report?

Because the UA report shows data by acquisition channel. The ad revenue from mediation platforms is ILRD (Impression Level Revenue Data), which can be tied to the channel the user came from, so it's the right basis for ROAS.

The dashboard has Ad Mediation and Ad Network revenue; use the former

Ad Network revenue is only complete if every monetization network is authorized via API one by one. For the full difference, normal gaps and how to troubleshoot, see Revenue metrics on the dashboard.

Revenue in the mediation dashboard but nothing in Tenjin?

Check the SDK listener integration first. Also go to DIAGNOSE → Health and look for "Unlinked Ad Placements"; link them to the right app.

Common Q&A

There are two ways to report purchases, depending on who collects the payment
PaymentRouteWhat's needed
Official store billingThe SDK's transaction APIMust include the receipt / signature. Without a receipt Tenjin can't validate with the store and the purchase is marked UNKNOWABLE. If you don't want receipt validation, turn on "Accept unvalidated purchases?" under the app's Settings → IAP Validation; purchases without a receipt then count as revenue and trigger purchase callbacks
Third-party paymentsS2S Purchase APINo client receipt or signature needed
Don't report the same purchase from both the SDK and your server

Otherwise revenue doubles. If you use S2S, remove the SDK-side reporting.

How do I check purchase events recorded by the SDK?

In the Raw Data Exporter, select purchase events to export recent purchases. The purchase_state field tells you whether each one passed validation.

IAP revenue on the dashboard is net of the store commission

The app's Settings → App Store Commission sets how much is deducted: 30% by default, settable by date range. iOS apps can also choose Dynamic to apply Apple's country / region rates automatically. When reconciling with your own revenue data, first make sure both sides use the same basis (before or after commission).

With S2S: if the price you send is already after the store's cut, add postcut=1 and Tenjin won't deduct it again.

Using RevenueCat or another third-party subscription platform?

RevenueCat: add your store credentials in Tenjin, then add Tenjin's SDK Key under Integrations in RevenueCat; no SDK changes needed. On iOS Tenjin deduplicates automatically, so you can turn on both the subscription and IAP callbacks. Android and other third-party platforms are not deduplicated yet: for each channel, turn on either the Subscription Revenue callback or the IAP callback, not both, or the channel will receive duplicate events.

Subscription-heavy Android app? Adjust the commission rate

Google Play takes 15% on subscriptions, while Tenjin's default Manual commission is 30%. If your Android app earns mostly from subscriptions, set App Store Commission to 15% (this rate also applies to one-time purchases). Also note that Tenjin doesn't deduct taxes and doesn't subtract refunds automatically yet, so numbers will differ from platforms like RevenueCat.

8Custom eventsOptional▶
What to doPlan the key events to report → instrument them in the SDK → for events that should go to channels, configure them by event name in callbacks
Custom in-app events

Common Q&A

Custom events only take integer values: no amounts, currencies or nested parameters

Tenjin is a marketing attribution tool, not a product analytics tool. Report revenue through the Purchase API in step 7. For complex, multi-dimensional event parameters, run Firebase / GameAnalytics alongside and join on Tenjin's Customer User ID.

Each app can have up to 500 custom events

Only send Tenjin the events that matter for campaign optimization (registration, tutorial complete, key levels, first purchase, etc.). Use a dedicated product analytics tool for large volumes of in-game tracking (such as hundreds of levels reported one by one), or you'll hit the limit quickly.

Also, the dashboard reports show roughly 30 custom events (prioritizing metrics you've saved and the most common events). With many events, some won't be findable in the dashboard and can only be seen in raw data. Contact us if you need specific events always shown.

Want to send an event to a channel?

Send the event from the SDK first; only then does it appear in the list of selectable events in callbacks.

1How an "install" is recorded▶

Tenjin does not count store downloads. It counts the first app open successfully reported by the SDK on the device. From the docs: "the first app_open event as the Install event and all subsequent app_open events are recorded for sessions."

This leads to a few frequently asked points:

  • A user who downloaded from the store but never opened the app → no install in Tenjin.
  • If the SDK isn't running, there's no data at all; nothing was reported.
  • acquired_at in raw data is the time of this first open, not the store download time. It's the anchor for all cohort metrics.

2Tracked vs Reported Installs: why the numbers differFrequent▶
MetricMeaningSource

Use Tracked Installs as your source of truth. It's Tenjin's independent third-party attribution, and the basis for billing and reporting. Reported Installs simply shows the channel's own number for comparison.

Normal gap: around 30% for self-attributing networks (SANs; Meta's docs give 30–40%), about 10% for other channels.

Why the two will always differ

The root cause: each channel only knows about its own campaigns, while attribution exists to look at all your channels together and decide which one each user belongs to. The five common reasons:

ReasonExplanation
Channels ignore third-party attribution decisionsLarge channels such as Meta and Google use their own technology to decide which installs are theirs. When a user saw ads on several channels, a third party can't get every channel to accept the final result.
Install callbacks or click tracking URLs not set up correctlyThe most common and easiest to fix. Go back to the channel's setup doc and check that callbacks and links are correct and working.
Uncertainty from probabilistic attributionWhen a channel can't collect device IDs (IDFA / GAID), users can only be matched probabilistically, which is inherently less accurate than deterministic matching.
Duplicate reporting from a channel SDK and the attribution SDKTenjin sends installs to the channel; if another channel SDK in the app also reports the install, the channel's Reported number may count it twice.
The channel uses different attribution logicMostly self-attributing networks, whose internal attribution is a black box.

For specific setup issues that widen the gap further, see Google Ads conversion actions and Meta AMM.

3Where organic installs come from▶

Tenjin uses last click plus view-through attribution. Clicks take priority over impressions; typical windows are 7 days for clicks and 24 hours for impressions, adjustable in the dashboard.

An install marked Organic means only one thing: no ad engagement matching this device was found within the attribution window.

So if organic installs look unusually high, check these three things first:

  1. Are ad clicks coming in?
  2. Are the channels you're running authorized and set up in the dashboard?
  3. Are device IDs being collected?

4Reinstalls and re-engagement▶
Re-engagement attribution Set up re-engagement measurement

The basics: every install generates a brand-new install ID (AIID, Analytics Installation ID, the key Tenjin records attribution under), so a reinstall naturally looks like a new user. Tenjin uses device IDs (GAID on Android, IDFA on iOS when ATT is allowed) to look up the device's earlier records and recognize it where possible.

Default behavior (re-engagement off)

CaseResult
Reinstall · recognizedKeeps its original attribution. No new conversion, no extra billing, no repeat callback to the channel; the user's later revenue stays with the campaign that originally acquired them
Reinstall · not recognizedThe original attribution can't be inherited, so it's attributed as if new. With no matching ad engagement it becomes Organic

When a reinstall can't be recognized

  • The iOS user declined ATT. Without IDFA the device can't be confirmed as the same one, so the reinstall is treated as a new install. This is the main case.
  • No GAID on Android (devices without Google services, or users who turned off ad personalization in system settings).
  • The device hasn't been seen for a long time. Device and attribution records aren't kept forever, so a device returning after a long gap is treated as a new user.

If you run retargeting / re-engagement campaigns

TypeWhat the user did
ReinstallDeleted the app, then installed it again
ReactivationKept the app but hadn't opened it in a while, then came back

To credit returning users to the retargeting campaign that brought them back, turn on Re-engagement yourself in the dashboard; it's off by default. Once on, a return is credited to the retargeting campaign only when all three conditions are met:

  1. Both the app and channel switches are on. The app switch is on the app page's Attribution tab (Enable Re-Engagements); the channel switch is in that channel's settings and only appears once we've enabled the channel, so contact us if you don't see it. Set this up a few days before the campaign starts.
  2. The user was inactive longer than the inactivity threshold: 7 days by default, configurable from 1 to 30 days, counted in full UTC calendar days. It applies to both reinstalls and reactivations.
  3. There was a qualifying paid ad engagement within the attribution window.

If any condition isn't met, the user keeps their existing attribution.

Only some campaigns on a channel are retargeting: for non-self-attributing channels, you can leave the channel switch off and add &retargeting=true to those campaigns' tracking links (the app switch must still be on). Self-attributing networks such as Google, Meta and TikTok only support the channel switch.

Callbacks: self-attributing networks need nothing extra; just keep the Install callback on. Other channels need a separate Re-engagement callback turned on so they can tell returning users from new ones.

Reporting: two new metrics, Tracked Re-engagements (returns credited to a paid campaign, including reinstalls and reactivations) and Tracked Reinstalls (reinstalls that resulted in a new attribution).

How credit is split: the original acquisition campaign keeps the install and everything the user did before returning. From the day of the return, the user's sessions and revenue count under the retargeting campaign, so the acquisition campaign's LTV / ROAS stops growing for that user. The retargeting campaign's cohort metrics start from the day of the return. It only applies to returns after the feature is turned on; earlier returns can't be recalculated. A longer threshold re-attributes fewer users and moves less credit away from acquisition campaigns.

5Time zone: UTC+0Frequent▶

The Tenjin dashboard uses UTC+0 throughout, and switching time zones isn't currently supported. This is also the default for most global UA products.

The main reason: ROI, ROAS and LTV depend on APIs from many ad and monetization channels, and some of them only provide UTC+0 data. To keep data consistent, Tenjin doesn't currently support switching time zones.

We also recommend choosing UTC+0 when opening ad accounts; it makes reconciling data much easier later.

Reconciliation rule: before comparing numbers from any two sources, make sure both are set to UTC+0 and cover exactly the same period. This is the most common, and easiest to rule out, cause of mismatched data.

6Cohort metrics: what N-Day means▶

Easy to spot: any metric with "N-Day" in its name is a cohort metric. For example, N-Day IAP LTV, N-Day Retention Rate, N-Day Ad ROAS. From the docs: "All N-Day metrics are cohorted metrics and grouped by Acquisition Date", i.e. by install date.

N can go from 0 up to 365. Metrics without N-Day (Spend, Tracked Installs, Revenue, etc.) are daily metrics counted on the day the event happened.

Don't compare the two kinds directly. "Revenue on July 1" and "7-day revenue from users who installed on July 1" are completely different numbers.

Two ways to calculate retention (dashboard path: My Account → Manage User → Cohort Strategy, at the bottom of the page):

How Day N is definedGood for
UTC (absolute)Day 1 starts at the first UTC midnight after the user's install, so Day 0 is the partial day of the installMatching other platforms that count in UTC, fewer definition gaps
Relative (default)Counted from each user's own install time in 24-hour blocks: 0–24h is Day 0, 25–48h is Day 1Reflecting users' real behavior, independent of install time of day

Make sure whoever reconciles the numbers knows which one you use; the same users will have different retention rates under the two methods.

What's the actual difference between Ad Mediation and Ad Network?

Ad Mediation (impression level): this number isn't calculated by Tenjin. After every ad impression, the mediation platform (AppLovin MAX, Unity LevelPlay, AdMob, TopOn, CAS, TradPlus, etc.) emits an impression-level revenue signal (ILRD, Impression Level Revenue Data) saying how much the winning bidder paid; the Tenjin SDK listens for it. Because each signal carries a user identifier, Tenjin can tie the revenue to a specific user and roll it up to the acquiring campaign / channel / app. In principle it should match your mediation dashboard.

Ad Network (settlement level): Tenjin calls each monetization network's reporting API to pull actual settled revenue per app per day, then allocates that total to acquisition channels by their share of sessions (every session within a channel / campaign is treated as equal). It's the money you actually get paid, but since it's allocated by sessions rather than measured per impression, it's inherently less precise for a single channel or user.

So: use Ad Mediation for ROAS and channel optimization. Each row in the UA report is an acquisition channel, and impression-level, user-linked Mediation revenue is the accurate per-channel view. Use Ad Network to check actual payouts, as a completeness benchmark, and to spot invalid traffic.

What each type of ad revenue requires

  • Ad Mediation needs: the mediation SDK in your app (MAX / TopOn / AdMob / TradPlus / LevelPlay, etc.) plus Tenjin's matching listener.
  • Ad Network needs: every monetization network added and authorized in the dashboard. Adding only your mediation platform's publisher account (e.g. AppLovin Publisher) doesn't pull settled revenue for all the networks it mediates; each network has to be added separately. Miss one and that revenue is missing entirely, which is the most common reason for a large gap.

How big a gap is normal?

The two methods will never match exactly, and a gap on its own doesn't mean something is wrong. Benign causes include the difference between the two methods, bid prices in ILRD being the mediation platform's estimates, time zone differences between mediation and networks, API reporting delays or later corrections, and small volumes where any absolute difference looks like a huge percentage.

A gap above 20% deserves attention. First check that every monetization network has been added; it could also be invalid traffic or an integration issue.

Anchor for troubleshooting: compare each of Tenjin's numbers with its own source of truth: Ad Mediation against the mediation dashboard (MAX / AdMob), Ad Network against the sum of the networks' dashboards. Whichever matches is the reliable one, and the problem is on the other side.

11Deferred deep links▶

What it solves: a user clicks an ad for specific content / a specific game, and after installing and opening the app they land straight on that page instead of the home screen.

Three parts:

  1. In the app, implement your own URL scheme (e.g. myschema://) and the routing from scheme to page. You implement the routing yourself; Tenjin only passes the value to you.
  2. On the link, append a deeplink_url parameter to the Tenjin tracking link, with a different value for each destination. For example:
    https://track.tenjin.io/v0/xxx/campaignid123?advertising_id={advertising_id}&click_id={click_id}&deeplink_url=myschema://shoe1
  3. In the SDK, call getAttributionInfo() after Connect(), read the value from the deferred_deeplink_url field and hand it to your router.

Important: this only works for users who don't have the app installed yet. For sending existing users to a page, see deep linking for retargeting campaigns.

How to test it yourself

  1. Register the device as a test device, and use a device that has never had the app installed.
  2. Copy a tracking link from any non-Meta channel, replace advertising_id with the device's ad ID, append &deeplink_url= plus your deep link (URL-encode it if it contains ? or &), and open it in the phone's browser.
  3. Install and open the app. The app doesn't need to be live: ignore a failed store redirect and install the test build via TestFlight / Xcode / adb.
  4. The app should open the matching page. In the dashboard, find this open event in the Live Event Tool → click the device ID → check Deferred Deeplink Url under Device Information.

Register a test device (to see whether events arrive)

Four rules to know:

  • Test device data doesn't go into reports. From the docs: "Any events sent through a test device… will not get recorded in the dashboard reporting." The tool is only for verification and doesn't pollute real data. Conversely, not seeing something in the Live Event Tool doesn't mean it didn't reach Tenjin; it may be in the raw data.
  • Don't test with TestFlight. Per Apple's policy, TestFlight uses a new advertising_id on every launch, so it never matches the registered device and events never show.
  • The Live Event Tool filters by the registered device ID. A changed bundle, a reinstall or a reset ad ID can all stop the old ID from matching; register again.
  • Channel callbacks can't be tested this way. Test devices only record test events coming into Tenjin; callbacks to channels only happen once real campaigns run and there are real attributed installs.

3Troubleshooting

Start here when numbers don't match.

AData discrepancy checklistMost used▶

Step one: rule out definition differences. Before any comparison, go through these four:

  1. Are both sides in UTC+0? The Tenjin dashboard is fixed at UTC+0. (See section 5)
  2. Is the date range exactly the same?
  3. Are you comparing the same kind of metric? Metrics with "N-Day" are cohort metrics grouped by install date; metrics without it are daily metrics counted on the day of the event. Don't compare the two. (See section 6)
  4. Tracked or Reported? Tracked is Tenjin's independent attribution; Reported is the channel's own number. They're different by design. Normal gap: around 30% for SANs (Meta 30–40%), about 10% for other channels. (See section 2)
Branch A: Tenjin installs don't match the channel's dashboard
  • Is the gap already within the normal range (around 30% for SANs / 10% for others)? If so, no need to dig further.
  • Google Ads: is ICM integrated on iOS? Without it, users who didn't opt in to ATT basically can't be attributed to Google. Is Firebase the primary conversion? If so, a bigger gap is expected. (See 3.2)
  • Meta: have the AMM terms been accepted? If not, campaign / creative breakdowns only show part of the data; look at the App / channel level totals. (See 3.1)
  • Health page: under DIAGNOSE → Health, are there "Unlinked Campaigns" (campaigns not linked to an app)? Data from unlinked campaigns won't appear under the app.
  • Callback switch: if the channel shows 0 installs, first confirm that channel's callback is switched on in Tenjin.
  • Callback Health: only green 100% means all callbacks were delivered; yellow or red means some were rejected by the channel. (See step 5)
  • Does the app also include the channel's own SDK? With both SDKs reporting, the channel's Reported number counts installs twice.
Branch B: lots of installs falling into Organic

An install marked Organic means only one thing: no ad engagement matching this device was found within the attribution window. Check these three, in order:

  1. Are ad clicks coming in? Check the click count on the campaign's detail page in Tenjin (non-self-attributing channels). If clicks are 0 and the channel Campaign ID keeps showing unknown, check the tracking link's macro mapping.
  2. Are the channels you're running authorized and set up in the dashboard?
  3. Are device IDs being collected? On Android, about 5% missing GAID is normal, and iOS users who decline ATT have no IDFA; but if close to 100% are missing, it's an integration problem.
Branch C: ad revenue doesn't match

First confirm which one you're comparing: Ad Mediation (from mediation) or Ad Network (from APIs). They work differently and won't match each other. (See section 7)

  • Treat a gap above 20% as a problem.
  • Ad Mediation is 0 or clearly low: is Tenjin's listener integrated? Are there Unlinked Ad Placements under DIAGNOSE → Health?
  • Ad Network is clearly low: has every monetization network been added and authorized separately? Adding only the mediation platform's publisher account isn't enough.
  • Totals are close, but D0 Ad ROAS differs a lot and converges by day 7/14/30: that's a methodology difference between the two, not a data problem. Use Ad Mediation for ROAS.
Branch D: IAP revenue doesn't match
  • Is "Valid Purchase Event" lit in the SDK integration status table? If not, receipts aren't arriving or aren't passing validation; check the receipt validation section of the IAP docs.
  • To see exactly which purchases have problems: export purchase events with Raw Data Export and check purchase_state to see whether each passed validation.
  • Total is low by a consistent percentage: IAP revenue on the Tenjin dashboard is net of store commission; check whether the other side is before or after commission. (See step 7)
Branch E: data looks partly missing / today's numbers aren't in yet

First check whether the metric is delayed by design: real-time metrics are Tracked Installs and SDK events; metrics updated every 2–3 hours are Spend, Reported Installs / Clicks / Impressions, and Ad Revenue (Ad Network). It's normal for these to look low on the current day. (See section 9)

Branch F: events don't show in the Live Event Tool
  • A newly registered test device can take up to 3 hours.
  • Is the registered ID right? IDFA on iOS; GAID on Android.
  • Testing with TestFlight? TestFlight changes advertising_id on every launch, so it never matches.
  • Changed bundle, reinstalled, or reset the ad ID? Register the device again.
  • Not in the Live Event Tool ≠ data didn't arrive. Check in Raw Data Export.
Branch G: your own API pulls don't match the dashboard
  • Add a 3-day lookback to scheduled jobs. Pulling T-1 too early, before ETL finishes, makes D0 revenue look low.
  • Set read_timeout to 180–300 seconds and per_page to 1000.

Still doesn't match? If you've checked all of the above, contact us with: app name and platform · exact date range · channels involved · screenshots of the setup steps you've completed · for reconciliation questions, screenshots from the other side.
