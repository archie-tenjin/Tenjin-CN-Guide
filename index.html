常见 Q&A

第三方安卓商店必须单独建 App

Google Play 和其它安卓商店（小米 / OPPO / vivo / 传音）在 Tenjin 里是两个独立的 App 实体，store type 选 Other，SDK 里用 TenjinSDK.AppStoreType.other 并使用对应 App 的 API key。

核心原则：SDK 里声明的 store type 必须严格等于面板里选的类型，不一致会直接报 {"code":404,"message":"no such app"}。

App 还没上架也能建

创建 Google Play 类型的 App 需要商店链接，先填一个占位链接创建，正式上架后回来更新即可。

建 Campaign 之前，App 和渠道都要先添加

否则新建 Campaign 时 App 下拉框会是空的（显示 No options）。

常见 Q&A

日志打印了不代表真的连上了

最常见的假象是客户端日志里有 Connect 字样，但面板上 SDK Key 显示 Last used: never、App Open 未收到——说明根本没有请求到达 Tenjin。

另外 Tenjin 的 Unity SDK 没有 "Init" 这个概念，只有 getInstance(key) + Connect()。

getAttributionInfo 返回空值或缺失字段，为什么？

归因并非即时完成。调用 connect() 之后，服务器必须接收请求、匹配点击并生成结果——几秒是行业标准延迟。如果你查询得太早，结果可能仍在计算中。请在客户端实现重试逻辑：

  • 不要延迟调用 connect()——请在隐私政策授权（Android）或 ATT 选择（iOS）之后立即调用
  • 在调用 connect() 之后的 2 至 3 秒再首次调用 getAttributionInfo
  • 如果响应为空或缺失关键字段，请等待 1 至 2 秒并重试
  • 将重试次数限制在 3 至 5 次
iOS：先 ATT 弹窗，后 SDK 初始化

SDK 在首次启动时就会记录 ATT 状态，如果此时用户还没点「允许」，记录到的就是未授权——会导致 ATT 授权率被严重低估。把 Tenjin SDK 初始化放在用户对 ATT 弹窗做出选择之后。

不要同时集成 Tenjin SDK 和 Meta SDK

两套 SDK 会重复上报，Meta 侧统计会乱。用 Tenjin 作为 MMP 就不要再装 Meta SDK；至少关闭 Meta 设置里的 autoLogAppEventsEnabled，停止默认发送收入 / 购买事件。

3渠道对接▶
做什么在面板添加渠道并授权 → 按渠道要求完成各自的配置 → 建 Campaign 和追踪链接（非自归因渠道）
添加渠道 创建 Campaign 与追踪链接
完成标准：渠道能拉到花费数据，且开始投放后能看到 Tracked Installs

先理解这一步在做什么：

  • 添加渠道并新建一个 campaign 的目的，是生成一条追踪链接，然后把这条链接复制到渠道后台。
  • 追踪链接的粒度看渠道要求。大多数渠道一条链接就够了，后续的 campaign 不需要在 Tenjin 里逐个添加，可以从渠道直接拉取；但部分渠道（例如 OPPO）要求每个 campaign 各自使用一条独立的追踪链接——渠道后台每新建一个 campaign，就要回 Tenjin 对应建一条链接，否则这个 campaign 的数据会归不到位。
  • 部分 SAN 自归因渠道没有追踪链接，看不到是正常的。

各家渠道对「活动（Campaign）」的叫法都不一样，对照表见 各渠道层级名称对照。

下面三节分别是 Meta、Google Ads、TikTok 和 其它渠道 的配置要点。

3.1渠道：Meta高频▶
Meta 渠道配置 Meta AMM 与 Tenjin
⚠️ 头号常见问题：AMM 授权

要解锁完整的活动报告 / 数据显示，需要满足以下任一条件：

① 达到最低流量门槛（>100 个独立用户 或 >100 次跟踪安装），或 ② 在 Meta Events Manager 接受 AMM（Advanced Mobile Measurement）条款。

两者都不满足时，Meta 会套用严格的隐私阈值，低于阈值的 campaign 数据会被 API 遮蔽——表现为 Meta 后台有几十上百个安装，Tenjin 不显示或部分不显示。建议在开始投放之前就把 AMM 签掉，不要等跑量。

3.2渠道：Google Ads高频▶
Google Ads 渠道配置
⚠️ 头号常见问题：Tenjin 的转化动作须设为 Primary

官方说明：将 Firebase 设置为主要转化事件，可能会导致 Tracked Installs 和 Reported Installs 之间的差异增大。

操作路径：Google Ads → 点开转化名（形如 你的包名 first_open）→ Edit Settings → 把 Action optimization 从 Secondary 改成 Primary。改完之后 Smart Bidding 需要 1–2 个转化周期重新学习，差异是逐步收敛的，不会立刻变好。这是过去几个月出现频次最高的单一问题。

从 Tenjin 导入转化事件（步骤 4）
多个 Google Ads 账户：每个 Link ID 各加一条回传

官方说明：「如果你有多个 Link IDs，点击 + ADD EVENTS → Advanced，然后为每个 Link ID 添加回传。」

在 Tenjin 面板添加 Link ID（步骤 3）
Google Ads 里选不到 Tenjin 作为转化来源？因为还没有真实安装量

即使关联已经建好、回传也加了，Google Ads 也要在该 Link ID 下真正收到过安装回传之后，才会把第三方应用分析放进可选来源列表。刚关联、零安装时必然看不到。

这不是配置错，发正式包、等真实安装进来后几小时到一天再回来选。

改不了转化动作？

先检查是不是 Manager Account（MCC）的权限限制，另外确认 campaign 目标选的是 "Installs"。

3.3渠道：TikTok▶
TikTok for Business 配置 TikTok 数据差异排查指引
TikTok 现在是自归因渠道，不再使用追踪链接

按新的集成文档走，不用找 tracking URL。

Tenjin 的 TikTok campaign 显示的是「广告组名（广告系列名）」

英文即 Ad Set Name (Campaign Name)。原因：按 campaign 层向 TikTok API 请求拿不到 platform 和 bundle_id，所以 Tenjin 只能按 Ad Group 层请求。这是报表架构限制，无法调整。

5回传配置重要▶
做什么配置发给渠道的回传 → 需要的话，配置发给自己服务器的 S2S 回传

怎么读 Callback Health

Callback Health 是判断「Tenjin 侧归因是否成功记录并发送给渠道」的主要标准。

显示含义
绿色 100%过去一天所有回传都成功发出，且都被对方成功接收
黄色 / 红色有部分回传发送了，但被渠道拒绝了
没有颜色和百分比这个事件在过去一天没有被触发过。这不一定代表故障——可能只是没有对应的事件需要被发送

点进具体的某一条 callback，可以看过去成功和失败传递的记录，也可以看过去一小时和过去一天尝试发送的事件次数。

常见 Q&A

要启用某个渠道的回传，必须先在该渠道下授权至少一个广告账户

但如果你不用 SDK、走纯 S2S 的事件上报，事件上报本身不需要任何渠道授权。如果 App 还在开发中没提交商店，Tenjin 侧的渠道配置可以等上线再做。

测试设备测不出回传记录

测试设备只记录进入 Tenjin 的测试事件；发给渠道的回传要等真实投放跑起来、且有真实归因安装之后才会产生。

常见 Q&A

聚合平台是接 SDK 插件，不是在面板「加渠道」

广告变现走的是独立的 SDK 插件集成——Tenjin 的 SDK 去监听聚合平台的展示事件。聚合平台不是单一投放渠道，不需要作为渠道添加。我们支持的聚合平台以及各自的接入代码都在文档里。

怎么区分买量渠道和变现渠道？

在 Add a Channel 界面，卡片右下角标注了 revenue 的就是变现渠道，标注了 attribution 和 spend 的是买量渠道。

为什么在 UA 面板里能看到广告变现收入？

因为 UA 面板是以买量渠道的维度展示数据的。聚合平台提供的广告收益是 ILRD（Impression Level Revenue Data，展示级收入数据），它能和这个用户是从哪个买量渠道来的绑定上，所以用来看 ROAS 比较合理。

面板上的广告收入有 Ad Mediation 和 Ad Network 两种，建议看前者

Ad Network 需要通过 API 逐个授权每一个变现渠道才能拿全。两者的完整区别、正常差异范围和排查方法见 三种收入指标。

聚合平台后台有收入但 Tenjin 里一分钱没有？

先检查 SDK 插件的集成，也可以去 Diagnose - Health 检查并连上缺失的广告位。

2规则与口径

Tenjin的产品业务逻辑和规则。

1一次「安装」是怎么被记下来的▶

Tenjin 记的不是应用商店的下载，而是 SDK 在设备上第一次成功上报的 app open。官方原文：「the first app_open event as the Install event and all subsequent app_open events are recorded for sessions.」——第一次 app open 记为安装，之后的 app open 都记为会话（session）。

由此推出几个常被问到的结论：

  • 用户在商店点了下载但从没打开过 app → Tenjin 里没有这次安装。
  • SDK 没跑起来 = 没有任何数据，根本没上报。
  • 原始数据里的 acquired_at 就是这个首次打开的时间，不是商店下载时间。它是所有同期群指标的锚点。
归因常见问题 用户归因总览

指标含义谁说了算

请以 Tracked Installs 为准。这是 Tenjin 作为第三方独立归因的结果，也是计费和出报表的口径。Reported Installs 只是把渠道自己的说法原样展示出来，方便你对照。

正常差异范围：自归因（SAN）渠道可达 30%，非自归因渠道约 10%。

为什么两者一定会有差

根本原因是：每个渠道只知道自己的投放，而归因的意义恰恰是同时看你所有渠道的活动，再决定每个用户到底该算谁的。具体到常见的五类原因：

原因说明
渠道忽视第三方归因的判定Meta、Google 等大渠道依托自身技术，会自行判定哪次激活归属于自己。当用户同时接触了多个渠道，第三方就很难让每一家都接受最终的归属结论。
激活回调（callback）或追踪链接（click tracking url）没配好最常见、也最容易修的一类。回到对应的渠道配置文档逐项复核回传和链接是否正确、是否在正常运行即可。
概率归因带来的不确定性当渠道不支持收集设备标识（IDFA / GAID）时，只能通过概率方式匹配用户，准确度天然低于确定性匹配。
渠道 SDK 与归因 SDK 重复上报Tenjin 会把激活回传给渠道；如果 App 里另有一个渠道 SDK 也发了一次激活，渠道侧的 Reported 就可能被记两次。
渠道使用了与我们不同的归因逻辑多见于自归因渠道，其内部归因是黑盒。

几个会把差异额外放大的具体配置问题，见 Google Ads 转化动作 和 Meta 的 AMM。

3自然量（Organic）是怎么来的▶

Tenjin 用的是末次点击 + 展示归因（last click and view-through）。点击优先于展示；常见窗口是点击 7 天、展示 24 小时，可在面板调整。

一个安装被记成 Organic，只意味着一件事：在归因窗口内，没有找到任何能匹配上这台设备的广告互动。

所以看到自然量异常高，先查这三件事：

  1. 广告点击有没有正常进来
  2. 投放的广告渠道有没有授权配置
  3. 设备标识有没有采到
用户归因总览 归因窗口设置
4用户重装会怎么算▶

底层情况：每一次安装都会生成一个全新的安装 ID（AIID，Analytics Installation ID，也是 Tenjin 记录归因的主键），所以重装天然长得像一个新用户。Tenjin 会用设备标识（Android 的 GAID、iOS 上已授权 ATT 的 IDFA）去查这台设备以前的安装记录，尽量把他认回来。

默认行为（不做任何额外配置时）

情况结果
重装 · 认出来了继承原来的归因。不产生新的转化、不重复计费、不重复回传给渠道；该用户后续的收入继续算在最初获取他的 campaign 名下
重装 · 认不出来无法继承原归因，只能当成一次全新的归因来判断。如果没有可匹配的广告互动，就归 Organic

什么情况下认不出来

  • iOS 用户拒绝了 ATT。拿不到 IDFA 就无法确认是同一台设备，这类重装会被当成新安装处理。这是最主要的一类。
  • Android 拿不到 GAID（无 Google 服务的设备，或用户在系统设置里关掉了广告个性化）。
  • 距离上一次活跃 2 年以上——这种情况会被当作一个全新用户。

如果你在投再营销 / 召回广告（需要单独开通）

类型用户做了什么
重装（Reinstall）把 App 删掉了，之后又装回来
回流（Reactivation）App 一直没删，只是很久没打开，后来又回来了

如果希望被广告拉回来的用户重新算到那个再营销 campaign 头上，这是一个独立的功能，需要提前联系我们开通，不是默认行为。开通后，以下三个条件全部满足，这次回归才会被记到你的 campaign 头上：

  1. 该 App 和该广告渠道的 re-engagement 都已开启。建议在 campaign 开始前几天就配好。
  2. 用户的沉寂时长超过不活跃阈值——默认 7 天，可设 1–30 天，按完整 UTC 自然日计算。重装和回流都适用这个阈值。
  3. 归因窗口内有一次有效的付费广告互动。

任何一条不满足，什么都不会变，用户保持原有的归因。付费的再营销转化和付费安装一样，计为一次付费转化。

不追溯：只对功能开启之后发生的回归生效，开启之前的回归无法补算。

归因是「移动」，不是「拆分」。一个用户在同一时间只归属于一个 campaign，一次归因会一直有效，直到下一次重新归因把它替换掉。当回归用户被重新归因到你的再营销 campaign 时，这个用户的全部功劳——包括历史 LTV——会整体离开原来的 campaign。

5时间口径：UTC-0高频▶

Tenjin 面板统一使用 UTC+0，目前不支持切换时区。这也是大部分全球投放产品的默认设置。

主要原因是 ROI、ROAS、LTV 等数据会依赖各广告和变现渠道的 API，而部分渠道只提供 UTC-0 数据。为了保证数据一致性，目前 Tenjin 暂时还不支持时区切换。自定义时区功能已经在排期中。

另外也建议媒体开户时尽量选择 UTC-0 时区，后续数据对齐会更稳定。

对账规范：拿任何一方的数据来比之前，先确认两边都调到了 UTC+0，并且比较的是同一个时间区间。这是「数据对不上」里最常见、也最容易排除的一个原因。

6同期群（Cohort）指标：N-Day 是什么意思▶

识别方法很简单：指标名里带「N-Day」的，就是同期群指标。例如 N-Day IAP LTV、N-Day Retention Rate、N-Day Ad ROAS。官方定义：「All N-Day metrics are cohorted metrics and grouped by Acquisition Date.」——全部按获取日期（也就是安装日）分组。

不带 N-Day 的指标（Spend、Tracked Installs、Revenue 等）是按事件发生当天统计的日常指标。

这两类不能混着比。「7 月 1 日的收入」和「7 月 1 日安装的用户带来的后续 7 日收入」是两个完全不同的数。

两种同期群算法（面板路径：My Account → Manage User → Cohort Strategy）：

怎么切分 Day N适合
UTC（绝对）Day 1 从用户安装时间之后的第一个 UTC 零点开始。所以 Day 0 是安装当天那段不完整的时间和其它按 UTC 统计的平台对齐，减少口径差异
Relative（相对，默认设置）从每个用户自己的安装时刻起算，每 24 小时为一天。0–24h 为 Day 0，25–48h 为 Day 1看用户真实的行为节奏，不受安装时点影响

要让做对账的人知道你选的是哪个——同一批用户在两种算法下的留存和 ROAS 数字必然不同。

Ad Mediation 与 Ad Network 到底差在哪

Ad Mediation（展示级）——这个数字不是 Tenjin 算出来的。聚合平台（AppLovin MAX、Unity LevelPlay、AdMob、TopOn、CAS、TradPlus 等）在每一次广告展示后，会发出一个展示级收入信号（ILRD，Impression Level Revenue Data），告诉 Tenjin 这次展示胜出方出了多少钱；Tenjin 的 SDK 负责监听它。因为每条信号都带用户标识，Tenjin 能把这笔收入绑定到具体的用户，再逐层汇总到买量的 campaign / 渠道 / App。原则上它应该和你在聚合平台后台看到的数字一致。

Ad Network（结算级）——Tenjin 调用每个变现渠道的报表 API，拉取 App / 日期级别的实际结算收入，然后按各买量渠道贡献的会话数占比把这笔总额分摊下去（同一渠道 / campaign 下的每个会话被视为等值）。它是「真正到账的钱」，但因为是按会话分摊而不是逐次展示测量的，落到单个买量渠道和单个用户身上时精度天然偏低。

所以：算 ROAS、做买量渠道优化，一律用 Ad Mediation。UA 报表里每一行是一个买量渠道，而展示级、绑定到用户的 Mediation 数字才是准确的分渠道视图。Ad Network 用来核对实际到账、做完整性基准，以及交叉发现异常流量。

两种收入各自的接入前提

  • Ad Mediation 需要：你的 App 里已集成聚合平台 SDK（MAX / TopOn / AdMob / TradPlus / LevelPlay 等），并且安装了 Tenjin 对应的监听插件。
  • Ad Network 需要：把每一个变现渠道都在面板里单独添加并授权。只加了聚合平台的变现平台账号（如 AppLovin Publisher）不等于就能拉到所有被聚合渠道的结算数据——每个变现渠道都要单独配。少加一个，那部分收入就完全不在里面，这是两边差异过大最常见的原因。
支持的聚合平台与插件代码 Ad Revenue 渠道 API 配置 两种 LTV 的区别 如何计算 IAA 收入

差多少算正常

两种计算逻辑永远不会分毫不差，有差异本身不代表出了问题。良性原因包括：两套逻辑本身的差别、ILRD 信号里的出价本就是聚合平台的估算值、聚合平台与渠道之间的时区差、API 报表延迟或事后修正、以及数据量小的时候任何绝对差额看起来都像巨大的百分比。

如果两者差距 20% 以上，应引起重视，首先排查所有变现渠道是否加全，也可能是异常流量、集成缺陷等。

排查的锚点：把 Tenjin 的两个数分别和它们各自的权威来源对——Ad Mediation 对聚合平台后台（MAX / AdMob），Ad Network 对各变现渠道后台之和。哪个对得上，哪个就是可信的那个，问题就定位在另一边。

11深度链接（Deferred Deep Link）▶

解决什么问题：用户点了你某个具体内容 / 游戏的广告，装完打开 App 之后直接落到那个页面，而不是默认首页。

三步：

  1. App 侧实现自己的 URL scheme（例如 myschema://），并写好从 scheme 到具体页面的路由逻辑。路由这一段是你们自己实现的，Tenjin 只负责把值传给你。
  2. 链接侧在 Tenjin 追踪链接后面追加 deeplink_url 参数，每个投放目标用不同的值。例如：
    https://track.tenjin.io/v0/xxx/campaignid123?advertising_id={advertising_id}&click_id={click_id}&deeplink_url=myschema://shoe1
  3. SDK 侧在 Connect() 之后调用 getAttributionInfo()，从返回结果的 deferred_deeplink_url 字段里取到这个值，交给你自己的路由。

重要边界：这个能力只服务尚未安装的用户。

12怎么做测试▶

登记测试设备（看事件有没有进来）

面板路径：Diagnose → Test Devices → + New Test Device

  1. 选择对应的 App，填入设备的广告 ID。iOS 填 IDFA，Android 填 GAID（iOS 设备也可填 IDFV）。
  2. 刚登记完会有一定延迟。官方要求：「please allow up to 3 hours before you fire the event」——最多等 3 小时再触发事件。
  3. 之后触发的事件会实时出现在 Live Event Tool 里。

四条必须知道的规则：

  • 测试设备的数据不会进报表。官方原文：「Any events sent through a test device… will not get recorded in the dashboard reporting.」这个工具只用来验证，不污染正式数据。反过来说，在 Live Event Tool 里看不到不代表数据没进系统——原始数据里可能是有的。
  • 不要用 TestFlight 测。按 Apple 政策，TestFlight 每次启动都会换一个新的 advertising_id，永远匹配不上登记的设备，事件也就永远不显示。
  • Live Event 是按登记的设备 ID 过滤的。换了 bundle、重装过、重置过广告 ID，都可能导致原来登记的 ID 不再匹配，需要重新登记。
  • 渠道回传测不出来。测试设备只记录进入 Tenjin 的测试事件；发给渠道的回传要等真实投放跑起来、且有真实归因安装之后才会产生。
检查 SDK 状态

做一次转化测试（看归因链路通不通）

如果要验证「点击 → 安装 → 归因」整条链路，用转化测试。

前提：App 已加入面板 · SDK 已成功集成 · 面板里激活回调已开启 · 用一台从未下载过这个 App 的设备。

3排查

数据对不上的时候，从这里开始。

A数据不一致排查清单最常用▶

第一步：先排除口径问题。任何对比开始之前，先过这四条：

  1. 两边时区都是 UTC+0 吗？Tenjin 面板固定 UTC+0。（见第 5 节）
  2. 比较的时间范围完全一致吗？
  3. 比的是同一类指标吗？指标名带「N-Day」的是同期群指标，按安装日分组；不带的是按事件发生当天统计的日常指标。这两类不能混着比。（见第 6 节）
  4. 比的是 Tracked 还是 Reported？Tracked 是 Tenjin 的独立归因结果，Reported 是渠道自己上报的，两者本来就不一样。正常差异：自归因（SAN）渠道可达 30%，非自归因渠道约 10%。（见第 2 节）
分支 A：Tenjin 的安装数和渠道后台对不上
  • 差异是否已经在正常范围内（SAN 30% / 非 SAN 10%）？在范围内就不必再查。
  • Google Ads：Tenjin 的转化动作设成 Primary 了吗？设 Firebase 为主要会让 Tracked 和 Reported 的差异明显变大。（见 3.2）
  • Meta：AMM 条款签了吗？Meta 可能会遮蔽一些数据。（见 3.1）
  • 回传开关：渠道后台显示安装为 0 的话，先确认 Tenjin 侧该渠道的回传开关是打开的。
  • Callback Health：绿色 100% 才代表回传全部成功送达；标黄或标红说明有部分被渠道拒绝了。（见步骤 5）
  • App 里是不是还装了渠道自己的 SDK？两套 SDK 都上报，会让渠道侧的 Reported 多记一次。
分支 B：安装大量落到 Organic / 自然量异常高

一个安装被记成 Organic 只有一个含义：归因窗口内没找到能匹配这台设备的广告互动。按顺序查这三件事：

  1. 广告点击有没有进来。去 Tenjin 面板上该 campaign 的详情页看点击数（非自归因）。如果点击是 0、渠道 Campaign ID 一直显示 unknown，去查追踪链接的宏映射。
  2. 投放的渠道有没有在面板里授权配置。
  3. 设备标识有没有采到。Android 约 5% 拿不到 GAID 属正常，iOS 拒绝 ATT 的用户拿不到 IDFA；但如果是接近 100% 采不到，那是集成问题。
分支 C：广告变现收入对不上

先确认你比的是哪个口径——Ad Mediation（来自聚合）还是 Ad Network（来自 API）。两者机制不同，本来就不会一致。（见第 7 节）

  • 差距 20% 以上按故障处理。
  • Ad Mediation 是 0 或明显偏低：Tenjin 的监听插件装了吗？Health 区块里是否有未映射的广告位？
  • Ad Network 明显偏低：每一个变现渠道都单独添加并授权了吗？只加聚合平台的发布商账号是不够的。
  • 总量接近，但 0 日 Ad ROAS 差很多、7/14/30 日又收敛：这是两种算法的方法论差异，不是数据问题。ROAS 请用 Ad Mediation。
分支 D：内购收入对不上
  • SDK 集成状态表里「Valid Purchase Event」亮了吗？没亮说明收据没送到或没通过校验——检查文档里的内购事件收据校验部分。
  • 想看具体是哪几笔有问题：用 Raw Data Export 导出 purchase 事件，看 purchase_state 字段判断是否通过了校验。
分支 E：数据看起来少了一块 / 今天的数还没出来

先确认这个指标本来有没有延迟：实时的是 Tracked Installs、SDK 上报的各类事件；每 2–3 小时更新一次的是 Spend、Reported Installs / Clicks / Impressions，以及 Ad Revenue（Ad Network）。这类数据当天看偏低是正常的。（见第 9 节）

分支 F：事件在 Live Event Tool 里看不到
  • 测试设备刚登记的话，最多要等 3 小时。
  • 登记的 ID 对吗？iOS 填 IDFA；Android 填 GAID。
  • 是不是用 TestFlight 在测？TestFlight 每次启动都换 advertising_id，永远匹配不上。
  • 换过 bundle、重装过、重置过广告 ID，都需要重新登记设备。
  • Live Event 里没有 ≠ 数据没进来，去 Raw Data Export 里确认。
分支 G：自己用 API 拉的数和面板对不上
  • 定时任务加 3 天回溯窗口。拉 T-1 数据太早，ETL 还没跑完，D0 收入会偏低。
  • read_timeout 设 180–300 秒，per_page 设 1000。
